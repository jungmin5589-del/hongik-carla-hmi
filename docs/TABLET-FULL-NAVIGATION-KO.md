# 아이패드에서 기존 Three.js 내비 전체 사용

2026-11-10. 사용자가 원한 것은 간단한 휴대폰 선택창이 아니라,
기존 차량 3D·지도·음악·홍익 AI가 함께 있는 내비게이션이었다.

## 연결

1. PC 주행 앱과 기존 모바일 게이트웨이를 실행한다.
2. PC에서 `http://127.0.0.1:8776/connect?view=tablet`을 연다.
3. 같은 Wi-Fi의 아이패드 Safari에서 QR을 스캔한다.
   직접 입력할 때는 `http://PC의IP:8776/m/navigation`과 PC의 현재 코드를 쓴다.
4. 기존 `/m/` 화면에서 이미 연결했다면 같은 Safari에서 새 주소를 열면 된다.
   유효한 기존 페어링 쿠키로 연결하며 다시 코드 입력이 필요하지 않다.
5. 가로 방향에서 사용한다. PC에서 준비한 현재 주행과 연결되며,
   출발·일시정지, 지도·3D 시점, 음악, 홍익 AI 설명·선택·실행을 사용할 수 있다.
6. 종료 후 ‘시나리오 선택으로’로 돌아가 다음 상황을 선택할 수 있다.

엔진 재시작·화질 설정·이전 위치로 초기화는 PC 운영자에게 남긴다.
현재 동작은 CARLA 중간발표 내비 기준이다. NuRec/다른 서버 API의 호환성을 보장하지 않는다.
기존 간단 동반 화면은 `/m/`에 유지한다. 시스템 푸시 설정은 이와 별도이며
전체 내비 경로를 새 홈 화면 PWA·잠금 알림 경로로 등록한 상태라고 주장하지 않는다.

## 구현

PC의 `/navigation` HTML과 같은 Three.js·내비·음악·홍익 AI 자산을 재사용한다.
아이패드가 자체 WebGL로 화면을 그리고 PC는 CARLA 주행을 계산한다.
영상으로 PC 화면을 스트리밍하거나 아이패드에서 CARLA 엔진을 실행하지 않는다.

원래의 8774 제어 서버는 loopback으로 유지한다. 이미 쓰던 8776/8777
게이트웨이에 명시적으로 연결된 기기만 전체 내비를 열 수 있도록 했다.
전체 화면은 가상 도로 형상·주변 객체·위치, 음악과 캐시 음성이 필요하므로
간단 동반 화면보다 많은 표시 데이터를 전달한다. 임의 파일·URL 프록시는 제공하지 않는다.
전체 내비용 쿠키는 HttpOnly·SameSite=Strict이며 기존 1대 페어링과 만료 정책을 따른다.
출발·일시정지는 현재 세션 ID를 확인하고, 시나리오 선택은 현재 주행 완료 후에만 허용한다.
PC의 방화벽·보안 설정을 변경하거나 8774 포트를 외부에 공개하지 않는다.

HTTP LAN에서 없는 `crypto.randomUUID`를 Web Crypto 난수 기반 UUID로 보완했다.
가로 화면의 도움 버튼과 3D 시점 버튼이 겹치지 않게 아이패드 쪽 위치만 조정했다.
음성·음악은 Safari의 실제 탭 동작 이후 재생한다.

## 확인한 범위

- 기존 모바일 및 새 접근·세션·경로 제한 Python 검사 23개 통과.
- 실제 LAN HTTP 주소, iPad 가로 크기·터치 설정의 격리 브라우저에서
  페어링 → 기존 Three.js 차량/지도 → 음악 재생 → Sohee 설명 → 선택·확인 요청을 검사했다.
- 화면 자료와 음악·음성은 실행 중인 PC의 실제 파일/상태에서 읽었다.
  이 브라우저 검사의 실행 명령은 격리된 모의 수신기로 보냈으므로
  실제 CARLA 행동 실행이나 실제 iPad Safari 검증과 구별한다.
- 사용자가 실제 아이패드에서 기존 내비 전체가 표시되는 것을 확인했다.
- 실제 4차로 정체에서 사용자가 아이패드로 ‘트럭과 거리 넓히기’를 실행했고,
  PC의 동일 세션이 lateral 대응 → 완료(achieved) → 정차로 이어지는 것을 확인했다.
  해당 확인 시 접촉 기록은 0건이었다. 모든 상황·선택지의 실기기 검증은 아니다.
- 실제 아이패드 오디오의 주관적 음질과 새 전체 내비의 잠금 알림은 별도 확인이 필요하다.

관련 코드: `tablet_navigation.py`, `tablet_boot.js`, `tablet_connect.html`,
`tablet_pc.html`, `mobile_gateway.py`.
